# Search-audit lessons — smsapp, 2026-10-30 (resume after the DNS move)

## 1. A browser probe that lied: Cloudflare 522 over HTTP/3 only

- **Case:** after moving `smsapp` to Cloudflare Pages, the shared automation Chrome got Cloudflare 522 (Karachi edge)
  on `smsapp-51m.pages.dev` while `curl` over HTTP/1.1 and HTTP/2 from the same machine and edge got 200, and other
  Pages sites loaded in that browser. The host advertises `alt-svc: h3`, and the browser's QUIC path to it failed.
- **Corrected probe:** a separate headless instance of the same binary with `--disable-quic` renders it normally.
  Never report a Pages site as down from the browser alone; check `curl --http2` first.
- **Target file:** `references/probes.md` (browser probes) and `aoneahsan-cccs-verification` (deploy checks).

## 2. A pattern variant: the old host keeps serving after a DNS move (SA-P01 / SA-P11)

- **Case:** once the custom domain moved from Firebase Hosting to Cloudflare Pages, the old `*.web.app` host still
  served the July build: a soft 404 (unknown paths 200), but its canonical and its sitemap already pointed at the new
  canonical host, so the duplicate signal is weak.
- **Check to add:** after any host move, probe the OLD default host too (`/nope-404-x`, canonical, sitemap `<loc>`
  host). A redirect or a disable of the old host is an owner decision when the project has stopped Firebase work.
- **Target file:** `references/issue-catalogue.md` (SA-P01 detection) and `references/surfaces.md` (old hosts).
